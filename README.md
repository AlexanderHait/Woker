# Intake

Самостоятельный сервис: принимает заявки по HTTP, мгновенно подтверждает приём и дальше
сам добивается доставки каждому получателю — повторяет с растущими паузами, переживает
перезапуск и показывает, что застряло.

Молча не теряется ничего: заявка, которую не удалось доставить, оказывается в
`/v1/problems`, а не в логе, который никто не читает.

---

## Запуск

На чистой машине, где есть Docker:

```bash
docker compose up
```

Это всё. Соберётся образ, поднимется PostgreSQL, накатится схема, запустятся API, два
воркера доставки и заглушка получателя.

| | |
|---|---|
| API | <http://localhost:8000> — интерактивная документация на `/docs` |
| Заглушка получателя | <http://localhost:9000> |
| PostgreSQL | `localhost:55432` (`intake` / `intake`) |

Если какой-то порт занят, их можно переопределить:
`API_PORT=8080 STUB_PORT=9090 DB_PORT=5555 docker compose up`.

`make up` делает то же самое с `--wait` — команда вернётся только когда всё
поднялось и здорово. `make down` останавливает всё и удаляет том с базой.

Готово, когда в логах появились три вещи: `database system is ready to accept connections`,
`Uvicorn running on http://0.0.0.0:8000` и **две** строки `worker ... starting`.

Одна оговорка про повторный запуск: `docker compose up` не пересобирает образ, который уже
существует. После `git pull` или правки кода нужен `docker compose up --build` (или `make up`,
он всегда с `--build`) — иначе поднимется прошлая сборка.

### Если в системе нет `make`

Он нужен только для сокращений. Полные эквиваленты:

| вместо | выполнить |
|---|---|
| `make up` | `docker compose up -d --build --wait` |
| `make down` | `docker compose down -v` |
| `make test` | `docker compose up -d --wait db` затем<br>`docker compose run --rm --build tests pytest -v` |
| `make demo` | `bash scripts/demo.sh` |
| `make logs` | `docker compose logs -f` |

### Без Docker

Нужен доступный PostgreSQL 14+. Схема накатывается сама при старте.

```bash
pip install -r requirements.txt
export INTAKE_DATABASE_URL=postgresql://intake:intake@localhost:5432/intake

uvicorn app.main:app --port 8000   # API
python -m app.run_worker           # воркер доставки, во втором терминале
uvicorn stub.main:app --port 9000  # заглушка получателя, в третьем
```

API и воркеры — отдельные процессы, как и в compose: воркеров можно запустить сколько
угодно, они договариваются только через базу.

## Попробовать

```bash
# Говорим заглушке вести себя нормально
curl -X PUT localhost:9000/control/crm -H 'Content-Type: application/json' \
     -d '{"mode": "ok"}'

# Отправляем заявку
curl -X POST localhost:8000/v1/requests -H 'Content-Type: application/json' -d '{
  "source_id": "landing",
  "idempotency_key": "lead-0001",
  "payload": {"name": "Иван", "phone": "+7 900 000-00-00", "comment": "перезвоните"},
  "recipients": [{"url": "http://stub:9000/hook/crm", "name": "crm"}]
}'
```

```json
{"request_id": "5e2c…", "duplicate": false, "received_at": "…",
 "recipient_count": 1, "has_recipients": true}
```

> **Адрес получателя — `http://stub:9000/...`, а не `localhost`.** С заглушкой вы
> общаетесь со своей машины, а *сервис* ходит к ней по сети compose, где она называется
> `stub`. Если написать там `localhost`, воркер постучится сам к себе.

Дальше смотрим, что происходит:

```bash
curl localhost:8000/v1/requests/<request_id>   # полный статус и журнал попыток
curl localhost:8000/v1/problems                 # что сейчас не в порядке
curl localhost:9000/received/crm                # что получатель реально получил
```

## Как прогнать сценарии из раздела 4

Два способа, оба самодостаточные.

**Автоматически, все десять, вместе с остальными тестами:**

```bash
make test
```

Гоняет весь набор в Docker против настоящего PostgreSQL (~1 минута). Седьмой сценарий
запускает воркер отдельным процессом и убивает его настоящим `SIGKILL`, девятый
прогоняет 500 заявок. Смотреть `tests/test_scenarios.py` — по одному тесту на строку
таблицы из задания.

**Руками, чтобы видеть глазами:**

```bash
make up
make demo        # scripts/demo.sh
```

Скрипт проходит все десять сценариев против поднятого стенда и печатает по каждому
доказательство. Занимает несколько минут — в основном ожидание настоящих таймаутов и
настоящих пауз между повторами.

Заглушка управляемая, так что любой сценарий можно воспроизвести самому:

```bash
curl -X PUT localhost:9000/control/crm -H 'Content-Type: application/json' -d '{"mode": "ok"}'
curl -X PUT localhost:9000/control/crm -d '{"mode": "error", "status_code": 500}'
curl -X PUT localhost:9000/control/crm -d '{"mode": "error", "fail_first": 3}'   # 3 раза упадёт, потом ок
curl -X PUT localhost:9000/control/crm -d '{"mode": "silent"}'                   # примет соединение и замолчит
curl -X PUT localhost:9000/control/crm -d '{"mode": "slow", "delay_seconds": 30}'

curl localhost:9000/received/crm/summary   # сколько пришло и не пришло ли что-то дважды
```

Пятый сценарий («лежит дольше лимита попыток») доходит до `failed` через полные сутки
повторов. Чтобы увидеть это за секунды, перезапустите воркеры с коротким бюджетом:

```bash
INTAKE_RETRY_MAX_ATTEMPTS=3 INTAKE_RETRY_BASE_SECONDS=1 docker compose up -d worker
```

Седьмой сценарий — это `make kill-workers`, затем `make restart-workers`.

## Ручки

| | |
|---|---|
| `POST /v1/requests` | Принять заявку. `201` если новая, `200` c `duplicate: true` на повтор. |
| `GET /v1/requests/{id}` | Всё, что известно: состояние по каждому получателю, число попыток, когда следующая, что ответил в последний раз, и полный журнал. |
| `GET /v1/problems` | Что не в порядке: не доставлено дольше заданного · в отказе · без получателей. Сначала то, что болит дольше всех. |
| `GET /v1/stats` | Счётчики за период: принято, доставлено, в очереди, в отказе, без получателей. |
| `POST /v1/requests/{id}/retry` | Попробовать эту заявку ещё раз прямо сейчас — всем получателям или названным. |
| `POST /v1/deliveries/retry` | Массовый повтор по фильтру: «CRM починили, добей всё, что накопилось». |
| `POST /v1/requests/{id}/recipients` | Дописать получателей заявке, принятой без них. |
| `GET /healthz` | Живость плюс политика повторов и таймауты, которые реально действуют. |
| `GET /readyz` | Готовность — проверяет базу. |

Полные схемы — на `/docs`.

**Обязательные поля на входе:** `source_id`, `idempotency_key` и непустой объект
`payload`. Внутри `payload` не требуется и не проверяется ничего — почему, написано
ниже и в записке.

Несколько живых примеров:

```bash
# Один получатель лежал, теперь починили - добиваем накопившееся
curl -X POST localhost:8000/v1/deliveries/retry -H 'Content-Type: application/json' \
     -d '{"status": ["failed"], "recipient_origin": "http://stub:9000"}'

# Одна заявка, один получатель
curl -X POST localhost:8000/v1/requests/<id>/retry -H 'Content-Type: application/json' \
     -d '{"recipients": ["crm"]}'

# Проблемы старше пяти минут
curl 'localhost:8000/v1/problems?stale_minutes=5'
```

## Как это устроено

### Очередь — это и есть хранилище

Три таблицы, никакого брокера:

- **`requests`** — строка на принятую заявку. `UNIQUE (source_id, idempotency_key)` —
  это и есть защита от дублей.
- **`deliveries`** — строка на пару *(заявка, получатель)*. Это очередь.
- **`delivery_attempts`** — журнал только на добавление, строка на каждую попытку HTTP.

```
pending ──захват──> in_flight ──2xx──────────> delivered
                        │
                        ├── неудача, бюджет есть ──> pending, next_attempt_at в будущем
                        ├── неудача, бюджет кончился > failed (лежит, видна, повторяема руками)
                        └── воркер умер ──────────> заберут, когда истечёт аренда
```

### Как работа раздаётся

Воркеры забирают строки через `SELECT … FOR UPDATE SKIP LOCKED`. Двум воркерам одна и
та же пара не достанется никогда, а заблокированная строка никого не тормозит —
следующий воркер просто берёт другую.

Захваченная строка несёт `lease_expires_at` — срок аренды. Если воркер умер, срок
истекает и строку может забрать любой другой. Это весь механизм восстановления после
падения: ни демона-уборщика, ни ручных действий, ни «сбросить зависшие». `kill -9`
посреди отправки — штатное событие.

Счётчик попыток увеличивается **в момент захвата**, а не после HTTP-запроса. Процесс,
умерший посреди попытки, всё равно её потратил — поэтому заявка, которая стабильно
роняет воркер, не может крутиться вечно.

### Один медленный получатель не задерживает остальных

Три вещи вместе:

1. Отправка асинхронная — получатель, отвечающий 30 секунд, занимает один слот из
   `worker_concurrency` и ноль процессора.
2. `max_claims_per_origin` ограничивает, сколько строк одного хоста-получателя можно
   забрать за раз, — поэтому получатель с завалом в тысячу заявок не выдавливает
   остальных из очереди.
3. `attempt_deadline_seconds` ограничивает, сколько слот вообще может быть занят.

Получатели группируются по *origin* (`схема://хост:порт`): когда лежит CRM, лежат все её
адреса разом.

### Расписание повторов

`5с, 10с, 20с, 40с, 80с, 160с, 320с, 640с, 1280с, 2560с`, дальше раз в час, всего 34
попытки — около **24.4 часов**, причём десять попыток укладываются в первые 85 минут.

Быстро в начале, потому что большинство сбоев — моргнувший деплой; терпеливо дальше,
потому что CRM, лежащую всю ночь, незачем долбить. Джиттер ±20%, чтобы поднявшийся
получатель не получил весь накопленный хвост в одну миллисекунду. То, что дефолты
реально переживают полчаса и сутки, проверяется тестом в `test_retry.py`.

### Дойдёт хотя бы раз, и получатель отличит повтор

В каждой попытке уходит `Idempotency-Key: <delivery_id>` — он одинаковый для всех
повторов этой пары *(заявка, получатель)* — и `X-Intake-Attempt`. Если воркер умер
между «отправили» и «записали», мы отправим ещё раз, и получатель сможет это опознать.
Прерванная попытка честно попадает в журнал как `outcome: "unknown"`, а не делается
вид, что её не было.

### Таймауты

`connect 5с`, `read 30с`, жёсткий потолок `45с` на попытку. Таймаут чтения щедрый
намеренно: получатель, отвечающий за 20 секунд, медленный, а не сломанный, и оборвать
его — значит сделать тот самый дубль звонка клиенту, ради недопущения которого сервис и
существует.

Настройки, способные молча сломать гарантию, отвергаются при старте — например аренда
короче попытки, при которой два воркера могли бы доставить одну заявку одновременно.
Смотреть `Settings.validate_invariants`.

## Настройки

Всё через переменные окружения `INTAKE_*`; справочник — `app/config.py`, частое собрано
в `.env.example`. Дефолты — ровно то, что описано выше.

| Переменная | По умолчанию | |
|---|---|---|
| `INTAKE_DATABASE_URL` | `postgresql://intake:intake@localhost:5432/intake` | |
| `INTAKE_RETRY_BASE_SECONDS` | `5` | Первая пауза |
| `INTAKE_RETRY_FACTOR` | `2` | Во сколько раз растёт |
| `INTAKE_RETRY_CAP_SECONDS` | `3600` | Самая длинная пауза |
| `INTAKE_RETRY_MAX_ATTEMPTS` | `34` | ≈24.4 ч повторов |
| `INTAKE_READ_TIMEOUT_SECONDS` | `30` | На попытку |
| `INTAKE_ATTEMPT_DEADLINE_SECONDS` | `45` | Жёсткий потолок на попытку |
| `INTAKE_LEASE_SECONDS` | `90` | Сколько строки упавшего воркера ждут подхвата |
| `INTAKE_WORKER_CONCURRENCY` | `32` | Отправок одновременно на воркер |
| `INTAKE_MAX_CLAIMS_PER_ORIGIN` | `4` | Ограничение справедливости на хост |
| `INTAKE_DEFAULT_STALE_MINUTES` | `15` | Когда «ещё не доставлено» становится проблемой |

`GET /healthz` показывает политику, которая реально действует, — гадать не нужно.

## Тесты

```bash
make test                                  # всё, в Docker
pytest                                     # против своего PostgreSQL
pytest -m scenario                         # только десять из раздела 4
pytest -m "not slow"                       # без SIGKILL и пачки на 500
```

117 тестов, около 40 секунд. Гоняются против настоящего PostgreSQL и настоящего
получателя на настоящем сокете: `SKIP LOCKED`, истечение аренды и таймауты чтения — это и
есть вся конструкция, мок не проверил бы ничего из этого. `INTAKE_DATABASE_URL` должен
указывать на базу, имя которой кончается на `_test`, — иначе набор откажется запускаться,
потому что он дропает схему.

### Проверка, что тесты не врут

Зелёный набор что-то значит только если он краснеет, когда код неправильный.

```bash
python scripts/mutation_check.py           # ~2 минуты
python scripts/mutation_check.py lease     # только про аренду
```

Скрипт по очереди ломает одну гарантию (аренда никогда не истекает, попытка не тратится
при захвате, бэкофф не растёт, получателю не уходит ключ идемпотентности, заявка без
получателей отвергается, …) и требует, чтобы каждый раз падал именно тот тест, который
обязан это заметить. Сейчас 12 поломок, ловятся все. Каждая правка откатывается в
`finally`, и в конце скрипт перепроверяет файлы.

Так была найдена настоящая дырка: ограничение справедливости по получателям можно было
превратить в ограничение пропускной способности, и ни один тест этого не замечал —
поломка «выживала». Дырку закрыл `tests/test_worker.py`.

## Что где лежит

```
app/
  config.py      настройки и инварианты, проверяемые при старте
  db.py          пул соединений, накатывание миграций
  intake.py      приём заявки: проверка, дедупликация, постановка в очередь
  queue.py       очередь — захват, аренда, переходы состояний, повторы
  worker.py      цикл доставки
  sender.py      одна HTTP-попытка и что считается успехом
  reporting.py   статус, список проблем, счётчики
  api.py         HTTP-ручки
  retry.py       расписание повторов
migrations/      обычные .sql, накатываются по порядку под advisory lock
stub/            управляемая заглушка получателя
tests/           модульные, интеграционные и десять сценариев
scripts/
  demo.sh            те же десять сценариев руками против поднятого стенда
  mutation_check.py  ломает гарантии по одной и проверяет, что тесты это ловят
```

`NOTES.md` — записка на 15 строк, как просило задание: что сделано и что нет, какие решения
принимал сам и где это сломается. `NOTES-details.md` — то же самое без сокращений, с замерами
и с пятью вопросами к вам в конце.
